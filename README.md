**Виконав:** студент

**Тема:** IDS/IPS — теорія, огляд поширених інструментів, практичне розгортання Suricata

## Мета роботи

Розібратися, що таке системи виявлення та запобігання вторгнень (IDS/IPS), чим відрізняються основні підходи до їхньої побудови, а потім на практиці підняти конкретний інструмент — Suricata: встановити його, налаштувати під власну мережу, підключити набір правил (сигнатур) та переконатися, що він реально ловить і легітимний, і навмисно згенерований підозрілий трафік.

## Теоретична частина

### Що таке IDS/IPS

IDS (Intrusion Detection System) і IPS (Intrusion Prevention System) — це програмні або апаратні засоби, які моніторять мережевий трафік у пошуках аномальної чи зловмисної активності. Різниця між ними — у реакції: IDS лише спостерігає й повідомляє про підозрілі події (за сигнатурами відомих атак або відхиленнями від типової поведінки), тоді як IPS здатен ще й автоматично блокувати або пом'якшувати виявлену загрозу. Обидва підходи використовують для захисту як цілої мережі, так і окремих хостів від вторгнень, експлуатації вразливостей і шкідливого ПЗ.

### Сигнатурний підхід проти аномального

- **Сигнатурні (знання-орієнтовані) IDS** шукають збіг трафіку з відомими шаблонами атак. Спрацювання сигнатури одразу дає адміністратору конкретну підказку — яка саме загроза виявлена (відоме шкідливе ПЗ, сканування портів, атака на конкретний сервіс тощо).
- **Аномальні (поведінкові) IDS** натомість спираються не на конкретні шаблони, а на базову лінію «нормальної» поведінки. Систему цікавить не стільки саме навантаження пакета, скільки контекст: наприклад, якщо користувач завжди заходить у мережу з одного регіону й звертається до одних і тих самих ресурсів, а потім раптово авторизується з зовсім іншої точки світу й лізе в чужі для себе дані — це вже привід для тривоги, навіть без збігу з жодною відомою сигнатурою.

На практиці обидва підходи часто реалізують схожими технічними засобами, а різниця — здебільшого в тому, на яких даних і за якою логікою система приймає рішення про тривогу.

### Мережеві (NIDS) і хостові (HIDS) рішення

- **NIDS (Network-based IDS)** аналізують увесь трафік певного сегмента мережі — копія трафіку зазвичай надходить через дзеркалювання портів на комутаторах чи маршрутизаторах. NIDS сам по собі не «зшиває» окремі події в загальну картину — за кореляцію логів із різних джерел зазвичай відповідає окрема система, SIEM.
- **HIDS (Host-based IDS)** натомість працюють на конкретному хості — це можуть бути антивіруси, засоби виявлення шпигунського ПЗ, брандмауери. Вони аналізують системні журнали, відстежують зміни ключових файлів і встановленого ПЗ, іноді — мережеві з'єднання самого хоста. Із часом HIDS переросли в повноцінні EDR-рішення, а для деяких стандартів відповідності (PCI DSS, HIPAA, ISO 27001) наявність HIDS з функцією моніторингу цілісності файлів — вимога.

### Огляд і порівняння поширених інструментів

У межах модуля розглянув кілька відомих представників обох категорій (NIDS та HIDS) і порівняв їх на високому рівні — за принципом роботи, зручністю розгортання та типовими сценаріями використання. Для практичної частини обрав саме **Suricata** — сучасний, багатопотоковий движок NIDS/NIPS з відкритим кодом, який підтримує глибокий аналіз протоколів прикладного рівня (HTTP, TLS/SSL, DNS тощо), має вбудований парсер JSON-логів (EVE) і активно підтримується спільнотою (репозиторій OISF).

Для практики розгорнув окрему віртуальну машину з Ubuntu 22 в Oracle VirtualBox (хостингове рішення теж підійшло б, але VM зручніша для ізольованого експериментування). У налаштуваннях виділив 4096 МБ пам'яті та перевірив порядок завантаження:

Після старту машини увійшов у систему й перевірив мережеві інтерфейси командою `ip a` — потрібно було знайти реальну IP-адресу, отриману по DHCP, та назву активного інтерфейса (в моєму випадку — `enp0s3`, адреса `192.168.0.101`):

Знаючи адресу, підключився до машини по SSH через MobaXTerm — далі вся робота велась саме через це віддалене з'єднання, а не з консолі VirtualBox:

![SSH-підключення до VM через MobaXTerm](screenshots/step1-ssh-mobaxterm.png)

### Крок 2. Встановлення Suricata

Встановив необхідні пакети та підключив офіційний репозиторій OISF, у якому підтримується стабільна гілка Suricata:

```
sudo apt-get install software-properties-common
sudo add-apt-repository ppa:oisf/suricata-stable
sudo apt update
sudo apt install suricata jq
```

`jq` тут одразу поставив разом із Suricata — цей інструмент знадобиться пізніше для зручного розбору логів у форматі JSON. Після встановлення перевірив версію та статус служби:

```
sudo suricata --build-info
sudo systemctl status suricata
```

Служба стартувала успішно й одразу перейшла в активний стан:

![Статус служби suricata після встановлення](screenshots/step2-systemctl-status.png)

### Крок 3. Налаштування конфігурації

Основний конфігураційний файл — `/etc/suricata/suricata.yaml`. З усього великого переліку параметрів на цьому етапі мене цікавили головним чином дві речі: змінна `HOME_NET`, яка описує «свою» мережу, і секція `af-packet`, яка відповідає за захоплення трафіку з конкретного інтерфейса.

```
sudo nano /etc/suricata/suricata.yaml
```

```
HOME_NET: "[192.168.0.0/24]"
...
af-packet:
  - interface: enp0s3
    cluster-id: 99
    cluster-type: cluster_flow
    defrag: yes
    use-mmap: yes
    tpacket-v3: yes
```

![Редагування suricata.yaml у nano](screenshots/step3-suricata-yaml.png)

Кілька моментів, на які звернув увагу під час налаштування:

- `HOME_NET` за замовчуванням уже включає типові приватні діапазони (RFC 1918); я лишив лише той, що реально відповідає моїй мережі — `192.168.0.0/24`, оскільки саме в нього входить адреса VM.
- В `af-packet` назва `interface` обов'язково має збігатися з реальним ім'ям мережевого інтерфейса (`enp0s3` у моєму випадку) — інакше Suricata просто не побачить трафік.
- Параметри `defrag`, `use-mmap` і `tpacket-v3` відповідають за продуктивність захоплення: дефрагментацію IP-пакетів, ввід/вивід через відображення пам'яті (mmap) та використання сучаснішої версії механізму TPACKET у Linux-ядрі відповідно.

### Крок 4. Встановлення сигнатур (правил)

Сама по собі Suricata без правил (сигнатур) нічого не виявить — правила потрібно окремо завантажити й підтримувати в актуальному стані. Для цього є вбудований інструмент `suricata-update`, який отримує та оновлює набори правил із зовнішніх джерел:

![Виконання suricata-update для завантаження сигнатур](screenshots/step4-suricata-update.png)

### Крок 5. Запуск Suricata та перевірка роботи

З уже встановленими правилами перезапустив службу і перевірив, що вона піднялась коректно:

```
sudo systemctl restart suricata
sudo tail /var/log/suricata/suricata.log
sudo tail -f /var/log/suricata/stats.log
```

У журналі відразу видно, що рушій запустився та створив окремі потоки під різні задачі — воркери для обробки пакетів (W), менеджери потоків (FM) та «переробники» потоків (FR); конкретна кількість залежить від параметрів системи. Файл `stats.log` оновлюється кожні 8 секунд і показує поточну статистику — скільки пакетів оброблено, який трафік розпізнано:

![Журнал і статистика роботи Suricata після перезапуску](screenshots/step5-suricata-running.png)

### Крок 6. Перевірка спрацювання сигнатур

Щоб переконатись, що Suricata дійсно ловить підозрілий трафік, а не просто «крутиться» без діла, скористався публічним тестовим ресурсом `testmynids.org` — він спеціально відповідає payload'ом, який відповідає готовій сигнатурі GPL ATTACK_RESPONSE:

```
curl http://testmynids.org/uid/index.html
```

![Запит curl до testmynids.org](screenshots/step6-curl-testmynids.png)

Паралельно в іншій сесії стежив за логом сповіщень:

```
sudo tail -f /var/log/suricata/fast.log
```

І дійсно, кожен виклик curl породив одразу дві тривоги — одну за фактом самого запиту через `curl` (класифіковано як «Attempted Information Leak» через нетиповий User-Agent), і другу — власне за сигнатурою `GPL ATTACK_RESPONSE id check returned root`, яка й підтверджує, що правило спрацювало саме так, як і задумано:

![Сповіщення в fast.log після запиту до testmynids.org](screenshots/step6-fast-log-alert.png)

### Крок 7. Формат логів EVE JSON

Окремо від «швидкого» текстового логу `fast.log`, Suricata вміє вести структурований журнал у форматі **EVE** (Extensible Event Format) — усі сповіщення, аномалії, метадані та інформація про файли пишуться в один JSON-файл. Це значно зручніше для подальшої автоматизованої обробки, ніж парсити текстові рядки регулярними виразами:

![Приклад запису у форматі EVE JSON](screenshots/step7-eve-json.png)

Щоб зручно читати такий вивід, і знадобився інструмент `jq`, встановлений іще на кроці 2. Коротко освіжив для себе, з чого складається JSON: **об'єкт** — це невпорядкований набір пар «ключ: значення» у фігурних дужках, а **масив** — впорядкований список значень (рядків, чисел, булевих значень, вкладених об'єктів чи `null`) у квадратних дужках. `jq` дозволяє: витягувати конкретні поля зі складної структури, фільтрувати записи за умовою, трансформувати структуру (додавати/видаляти/змінювати поля), форматувати вивід для читабельності, а також вбудовувати ці операції в конвеєри обробки логів і скрипти автоматизації — від налагодження відповідей API до підготовки даних для звітів і візуалізацій.

![Ще один приклад структури EVE JSON-логу](screenshots/step7a-eve-json-2.png)

### Крок 8. Формат правил Suricata

Перш ніж писати власні сигнатури, розібрався зі структурою правила Suricata — вона складається з трьох частин: **дії** (що робити при збігу), **заголовка** (протокол, IP-адреси, порти й напрямок трафіку) і **опцій правила** (деталі умови збігу). Приклад типового правила:

```
alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"HTTP GET Request Containing Rule in URI"; flow:established,to_server; http.method; content:"GET"; http.uri; content:"rule"; fast_pattern; classtype:bad-unknown; sid:123; rev:1;)
```

![Розбір структури правила Suricata](screenshots/step8-rule-format.png)

### Крок 9. Створення власних правил

Далі вирішив написати пару своїх, навчальних правил і підключити їх окремим файлом `local.rules`:

```
root@mate:/var/lib/suricata/rules# nano local.rules
```

```
alert http any any -> any any (msg: "do not read gossip during work"; flow: to_client, established; classtype: policy-violation; sid: 10001; rev: 1;)
alert icmp any any -> any any (msg: "finally pinged"; sid: 10002; rev: 1;)
```

Перше правило — навмисно жартівливе (перевірка на HTTP-трафік), друге — просте сповіщення про будь-який ICMP (ping). Щоб Suricata підхопила цей файл, додав його до списку правил в основній конфігурації:

```
root@mate:/var/lib/suricata/rules# nano /etc/suricata/suricata.yaml
```

```
default-rule-path: /var/lib/suricata/rules

rule-files:
  - suricata.rules
  - local.rules
```

### Крок 10. Запуск з власними правилами у verbose-режимі

Для перевірки, що нові правила підхопились без помилок, запустив Suricata вручну, вказавши конфігурацію та інтерфейс явно, з детальним виводом:

```
root@mate:/var/lib/suricata/rules# suricata -c /etc/suricata/suricata.yaml -i enp0s3 -v
```

![Запуск Suricata у verbose-режимі з явним конфігом та інтерфейсом](screenshots/step10-suricata-verbose-run.png)

### Крок 11. Власні правила в дії

Останній крок — переконатись, що обидва власні правила реально спрацьовують. Знову підписався на `fast.log`:

```
student@mate: :~$ tail -f /var/log/suricata/fast.log
```

Крім знайомих уже алертів на кшталт `ET POLICY GNU/Linux APT User-Agent` (звичайний трафік оновлення пакетів) та кількох ICMPv6-подій, у журналі з'явились і мої власні правила: `finally pinged` спрацьовувало на ping-запити (і IPv4, і IPv6), а `do not read gossip during work` — на HTTP-трафік із сусідньої машини в мережі. Обидва власноруч написані сигнатури відпрацювали саме так, як і планувалось:

## Підсумки та висновок

За цю практичну роботу пройшов повний цикл роботи з мережевою IDS/IPS-системою — від теоретичної різниці між сигнатурним і поведінковим підходом до реального розгортання Suricata: встановлення, налаштування під конкретну мережу й інтерфейс, підключення готового набору сигнатур, перевірку роботи на реальному тестовому трафіку (`testmynids.org`) і, нарешті, написання й перевірку власних правил.

Найкорисніший практичний висновок — сама лише встановлена й запущена Suricata нічого не гарантує: без актуальних і правильно підключених правил (`suricata-update`, `local.rules` у `rule-files`) система просто мовчатиме навіть на очевидно підозрілий трафік. Так само важливо, що конфігурація (`HOME_NET`, правильний мережевий інтерфейс в `af-packet`) має точно відповідати реальному оточенню — інакше рушій або взагалі не побачить трафік, або даватиме хибну картину того, який трафік вважати «своїм», а який — зовнішнім. І, нарешті, формат EVE JSON разом із `jq` виявився набагато зручнішим для будь-якої подальшої автоматизованої обробки логів, ніж парсинг текстового `fast.log` вручну.
